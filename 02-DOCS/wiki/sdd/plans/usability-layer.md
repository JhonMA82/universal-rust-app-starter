# Plan — Usability layer (increment 1: agent-ready generated projects)

## 0. Global constraints

- Slug: usability-layer. Spec: 02-DOCS/wiki/sdd/specs/usability-layer.md.
- Stack: Python generator/tools, Rust templates. No framework syntax in this plan.
- Preserve module.json contract and composition pipeline.
- Generated projects must remain autonomous.

## 1. Context & constraints

- Constitution principles 2-4, 6, 8. Spec acceptance criteria: COMPOSITION.md lists modules/entrypoints;
  check_agents passes; AGENTS.md names architecture/domain/infrastructure/catalog/extension/verification/skills;
  unselected capabilities not announced; verification matrix passes.

## 2. Architecture

Increment 1 components:

A. **Capability inventory generator** — extend `composition_guide()` in `generator/compose.py` to emit
   a machine-readable `docs/CAPABILITIES.md` (or extend COMPOSITION.md) listing each installed module's
   id, version, description, documentation path, checks, and declared features. Derived from composition,
   not hand-maintained.

B. **Composition-aware AGENTS.md** — modify template `AGENTS.md` files (or append during generation)
   so the generated AGENTS.md references the composition inventory, architecture doc, extension points,
   and the reuse policy. Keep generic boilerplate; append a "Capabilities & extension" section.

C. **Skill selection by capability** — extend `integration.install` / profile skill logic so modules
   can declare `skills` in module.json, merged into the generated `.agents/skills/` set. Profile skills
   remain baseline; module skills add capability-specific skills when available.

D. **Documentation consistency check** — extend `tools/check_docs.py` (or add a check) to verify
   generated COMPOSITION.md/AGENTS.md mention installed modules and no uninstalled ones.

## 3. Interfaces & contracts

- `composition_guide(profile, preset, interfaces, modules)` → also produce capability inventory text.
- `module.json` optional field `skills: [str]` (list of skill ids present in starter's skills dir).
- Generation step copies skill directories listed by modules into `.agents/skills/` if not present.
- AGENTS.md append: "\n## Capabilities\nSee docs/COMPOSITION.md and docs/CAPABILITIES.md.\n" + reuse policy.

## 4. Data model & flow

- Modules already declare `documentation`, `description`, `checks`, `features`. Inventory derived from these.
- Skills: module declares skill ids; generator resolves to `.agents/skills/<id>/SKILL.md` in starter
  (if exists) and copies. Missing skill → warning, not failure (autonomy preserved).

## 5. Testing strategy

- Unit: `composition_guide` output contains module ids.
- Composition test: generated project COMPOSITION.md contains installed module names.
- check_agents: skills present.
- check_docs: no drift.

## 6. Sequencing

1. Extend composition_guide + add CAPABILITIES.md generation.
2. Append capabilities section to AGENTS.md/README.md during generation.
3. Add `skills` field to module.json schema (optional) and copy logic.
4. Add at least one module declaring a skill (e.g., desktop-shell declares egui skills already in profile).
5. Extend check_docs for inventory consistency.
6. Run verification matrix.

## 7. Risks

- Copying skills into generated projects bloats them; only copy when module declares. Mitigation: optional field, skip missing.
- AGENTS.md append must not break check_agents (it checks cargo commands present). Mitigation: keep existing.
- check_docs may not exist for generated projects (it's a starter tool). Mitigation: add generated-side check or rely on check_agents.

## Decisions

- Skills copied as directories (not symlinks) into generated projects to preserve autonomy (no starter dependency).
- Capability inventory is COMPOSITION.md + CAPABILITIES.md, both derived.
